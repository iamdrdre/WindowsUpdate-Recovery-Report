# 踩坑总结与安全边界

## 错误码不是完整诊断

同一操作可能出现多层错误。下载日志中的 `0x80004002` 是最终返回值，但前面的 `0x80070422` 和“Connect to the DO service”才揭示本案的直接阻断点。不要只对照一个十六进制代码就执行通用修复脚本。

## 一个故障修好后，可能露出下一个

恢复 `DoSvc` 解决了下载失败。先后出现的0x800F0982与0x800F0991属于安装阶段；后者CBS明确指向所需组件文件缺失与基线恢复失败，但不能确定最初损坏来源。DISM/SFC完成后仍要重新尝试并读取新日志。

## 组件存储修复成功不等于目标更新安装成功

`RestoreHealth` 的“操作成功完成”表示该操作完成，不保证某个累积更新的补丁载荷、语言资源或适用性检查已经通过。验证目标必须看安装历史或 CBS 后续结果。

## 升级空间要看峰值

第一次升级失败时，C 盘并非零空间，但安装日志显示阶段性需求超过当时可用空间约2.94 GiB。预留比日志最低估算更多的余量更稳妥，并确保临时文件能留在系统盘。不要因为 ISO 存在 D 盘就假设升级暂存也都写到 D 盘。

## 清理应用数据先备份并验证

目录名看起来像用户数据也可能含本地数据库、草稿、历史记录或应用设置。推荐流程：

1. 用户明确确认该应用数据可清理。
2. 保存工作并退出应用，确认相关进程退出。
3. 复制到有空间的保存位置。本案用D盘，但没有证明它是独立物理硬盘，不能据此声称有独立故障保护。
4. 校验文件数量、总大小和内容哈希；长路径、锁定文件或校验报错都应停止删除。
5. 校验全部通过后再删源目录，保留备份直到应用和文件验证无误。

本案 WPS 的 `cache.db` 被 `wps.exe` 占用导致校验中断，因此没有据不完整校验删除源数据。不要对用户目录套用“忽略错误继续删除”。

## 不要公开原始日志或截图

原始材料可能带有 Windows 用户名、邮箱、产品密钥、设备名、完整路径、更新 GUID 或应用历史。发布前进行脱敏，只保留解释故障所需的最少几行证据。检查仓库所有文件和 Git 历史，不要仅检查 README。

## 个案边界

- 不能证明问题从 2024 年起一直由同一根因导致；历史事件日志只保留了有限时间。
- `WubLock`、服务状态和 ACL 支持更新屏蔽配置的推断，不足以确认特定程序或操作者。
- 用户已确认最终系统更新成功；本复盘没有另行采集更新后的构建号或连续多轮更新记录。
- 本案命令是记录和检查流程，不是微软对所有机器的通用处方。
