# 从 `0x80004002` 到最终更新成功：一次 Windows 更新故障的排查记录

我的 Windows 11 电脑长期无法正常更新。最开始只看到一个错误码：`0x80004002`。后来才发现，整个过程不是一个故障，而是下载、更新包修复、系统升级空间不足几个阶段的问题接连出现。

这篇记录按排查顺序写下关键证据和踩坑点。它是一次真实个案，不是“复制一段命令就能修好所有电脑”的教程。

## 一开始：下载反复失败

更新历史里连续出现下载错误 `0x80004002`。单看这个代码，很容易去网上找一串重置更新组件的命令。但检查 Windows Update 日志后，关键线索在它前面：

```text
Connect to the DO service [0x80070422]
Exit Code: 0x80246008, Extended Code: 0x80070422
Method failed [0x80004002]
```

也就是说，最外层报错并没有直接告诉我哪里坏了；日志里的 `0x80070422` 才指向 Delivery Optimization 服务 `DoSvc` 被禁用。

进一步检查发现，`DoSvc` 与 `WaaSMedicSvc` 的注册表配置被锁成只读，普通的服务配置和注册表写入都返回“拒绝访问”。这看起来像更新屏蔽配置留下的痕迹，但没有证据能证明具体是哪一个工具、谁设置的，或者问题从哪一天开始。

备份服务配置后，我按步骤恢复了 `DoSvc`。重启后服务显示 RUNNING，更新终于可以下载。**这只修复了下载阶段，并不代表更新本身已经能安装。**

## 下载好了，安装还是失败

代表性更新 KB5043145 下载到100%后，安装一度停在76%，但 CBS 仍在处理更新。随后先遇到0x800F0982，重试又报0x800F0991；缺少前一错误的充分上下文，不能仅凭代码变化认定原因相同。

后续 CBS 指向简体中文资源文件 `wmpnetwk.mfl`：安装时无法取得所需组件文件，基线恢复失败，错误为 `PSFX_E_MISSING_PAYLOAD_FILE`。这定位了安装阻断点，但不能证明最初缺失来源或直接断言下载包损坏。

DISM `/CheckHealth` 说组件存储可修复。之后运行 `/RestoreHealth` 时进度曾停在 3.8%，但继续等待后到达 100%，并报告成功；`sfc /scannow` 也报告找到并修复损坏文件。可是目标更新后来仍然失败。这里学到的是：**修复命令完成，不等于特定更新包已经装好。**要看它之后生成的新 CBS 记录。

## 转向安装介质：先确认版本与语言

为了修复安装，下载了 Windows 11 ISO。ISO 保存在 D 盘，挂载后 Windows 给虚拟 DVD 分配了 F 盘符。F 不是多出来的实体硬盘；它是 ISO 挂载后出现的光盘卷。通过 `DISM /Get-WimInfo` 核对，介质包含“Windows 11 家庭中文版”，与当前版本相符。


## 真正阻止第一次升级的，是 C 盘空间

第一次就地升级没有完成，回滚代码为 `0x80070070 - 0x2000A`。`setuperr.log` 里出现不少 Error 行，看起来很吓人；但 `setupact.log` 给了更直接的数字：

- 安装阶段估算需要约 13.02 GiB。
- 当时系统盘只有约 10.07 GiB 可用。
- 空间缺口约 2.94 GiB。

所以这次回滚有明确的磁盘空间证据。某些其他错误行只是清理、迁移或可选组件提示，不能不看上下文就全部当成根因。

磁盘清理工具一度只显示可释放几十 MB，于是改为先统计目录大小。我选择清理确认不需要的应用用户数据、保留应用本体；数据先复制到 D 盘，逐文件校验后才清理原目录。Windows PowerShell 长路径处理一度让 Cursor 校验报错，切换 PowerShell 7 后通过。WPS 数据库又被 wps.exe 占用，校验中断，因此没有继续删除源目录。

之后系统盘报告剩余 40.6 GB，ISO 也仍在 D 盘。这次重新安装时，在“获取更新”处停留，我选择取消，等清理完成后重开，选择“不是现在”获取更新。这只是跳过在线动态更新检查，空间问题靠此前腾出空间处理。最终确认“保留个人文件和应用”后继续安装，系统更新成功。升级后的构建号没有另外留存，也没有单独核对旧 KB5043145 是否安装成功。

## 这次排查我会记住的几件事

1. 不要只盯着最后一个错误码。日志中前一个服务错误可能更接近根因。
2. 下载失败、安装时无法取得所需组件文件、升级空间不足，是不同阶段的问题；一个解决后，才有机会继续定位下一个。
3. 卡在某个百分比先查日志。百分比可能长时间不动，但系统仍在处理。
4. DISM 和 SFC 输出“成功”后，还要按目标更新重新验证。
5. 安装失败时读 `setupact.log` 的失败阶段和空间估算，别被 `setuperr.log` 里的所有错误行带跑。
6. 清用户数据先停应用、备份、校验；文件被占用或哈希失败就停止删除。
7. 最终结果要由版本号、更新历史和新日志确认，不能凭“安装程序走到某一页”宣布修复完成。

命令清单和脱敏后的证据摘要见 [`command-playbook.md`](command-playbook.md) 与 [`incident-report.md`](incident-report.md)。
